Ghost Network Watch is an independent public-interest project that audits the machine-readable provider directory files that health insurers are required to publish under 45 CFR 156.230(c). It is operated by one person and takes no money from insurers. The site is https://ghostnetworkwatch.org and the pipeline is open source at https://github.com/ghost-network-watch/ghost-network-watch.

WHO WE EMAIL AND HOW WE GOT THE ADDRESSES. Approximately 185 recipients, one per health insurance issuer. Every address comes from CMS's own Machine-Readable URL Public Use File, a federal government dataset in which each issuer publishes the technical contact address it wants used for questions about these exact files. These are corporate role addresses at insurance companies, for example a data engineering or IT applications team. No consumer addresses, no purchased lists, no scraped addresses, and no individuals.

WHY THEY EXPECT IT. Before we publish findings about an insurer's directory file, we send that insurer its own findings and at least 14 days to review or dispute them. This is a right-of-reply notice, which is standard practice for public-interest reporting, and the recipient is the contact the insurer itself nominated for this subject matter. The message identifies the project, states the publication date, and provides a reply path.

CONTENT AND FREQUENCY. One message per issuer per publication cycle. The first send is roughly 185 messages in October 2026, ahead of a publication date of 26 October 2026. After that, monthly at most, and only to issuers whose findings changed. Each message is plain text with compressed CSV attachments containing that issuer's own evidence rows. No marketing, no promotions, no tracking pixels, no images.

BOUNCE AND COMPLAINT HANDLING. Sending goes through a configuration set (gnw-notify) with bounce, complaint, reject and rendering-failure events delivered to an SNS topic that reaches a monitored inbox. We keep a per-issuer send ledger recording the SES message ID for each accepted message, so we can tell exactly which issuers were reached. Because a bounce means an issuer was never actually notified, we treat bounces as blocking rather than as noise, and we correct the address or find another route before publishing anything about that issuer. Hard bounces are not retried to the same address. The account-level suppression list stays enabled. Any recipient who asks to stop receiving these notices is removed, and we then contact that issuer through CMS instead.

VOLUME. Peak approximately 185 messages in a single day, then well under 200 per month. Measured across the full set built from our most recent crawl, messages run from 4 KB to 3.8 MB with a median of 0.12 MB, and 90 MB in total. The spread comes from the evidence attachments: an issuer with a clean directory file gets a short message, and an issuer with many flagged records gets a larger one.

We have dry-run the full send and verified that every message builds and stays under the size limit before requesting production access. Sending is a deliberate manual step, guarded by a script that refuses to run against the wrong AWS account, refuses while the account is in the sandbox, and keeps a per-issuer ledger so an interrupted run resumes instead of notifying anyone twice.
